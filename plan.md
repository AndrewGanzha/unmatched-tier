# План разработки приложения для проведения боев в Unmatched

## 1. Продуктовая рамка

Приложение проектируется как административная панель для организации и учета офлайн-матчей по Unmatched, а не как цифровая реализация всей настольной игры.

Цель первой версии:

- проводить матчи `1v1`
- проводить матчи `2v2`
- создавать турниры в этих двух режимах
- вести общий рейтинг игроков
- автоматически подбирать доступных персонажей на основе рейтинга игроков и силы персонажей
- хранить историю матчей, турниров и изменений рейтинга
- поддерживать авторизацию пользователей

Что не входит в первую версию:

- цифровое поле боя
- розыгрыш карт и симуляция ходов
- трекинг игровой партии по всем правилам настолки
- режим `FFA` на 3-4 игроков
- баны персонажей как обязательный сценарий

## 2. Зафиксированные продуктовые решения

- Рейтинг игроков: общий, без сезонного деления.
- Подбор персонажей: автоматический.
- Баны персонажей: не нужны в первой версии, но архитектура должна позволить добавить их позже без переделки ядра.
- Повторное использование персонажа в турнире: разрешено без ограничений.
- Авторизация: обязательна.
- Игровые режимы первой версии: только `1v1` и `2v2`.

## 3. Основные модули системы

### 3.1 Пользователи и авторизация

Нужно реализовать:

- регистрацию и вход
- роли пользователей
- защищенный доступ к административным действиям
- привязку матчей, турниров и рейтинговых изменений к конкретным пользователям

Минимальный набор ролей:

- `admin` — управляет игроками, персонажами, матчами, турнирами и настройками правил
- `player` — имеет профиль, видит свою статистику и участвует в матчах

На будущее стоит предусмотреть возможность расширения ролей, например до `moderator`.

### 3.2 Игроки

Для игрока нужно хранить:

- имя
- учетную запись
- текущий рейтинг
- статистику побед и поражений
- историю матчей
- историю изменения рейтинга

### 3.3 Персонажи

Для каждого персонажа нужно хранить:

- имя
- тир (`S`, `A`, `B`, `C`, `D` и т.д.)
- числовую силу `power_score`
- статус активности
- дополнительные флаги для будущих правил

`power_score` нужен не только для отображения, но и для алгоритма автоматического подбора.

### 3.4 Матчи

Матч должен поддерживать:

- режим `1v1` или `2v2`
- состав участников
- выбранных персонажей
- статус матча
- победителя
- перерасчет рейтинга после завершения

Рекомендуемые статусы:

- `draft`
- `ready`
- `finished`
- `rated`
- `cancelled`

### 3.5 Турниры

В первой версии достаточно поддержать:

- турнир `1v1`
- турнир `2v2`
- формат `single elimination`
- посев участников по рейтингу
- ручную корректировку сетки администратором

Важно: матч в турнире должен быть обычным матчем системы, а не отдельной сущностью с дублирующей логикой.

### 3.6 Рейтинг

Рейтинг нужно считать централизованно и прозрачно.

Для первой версии подойдет модель `Elo`, потому что она:

- проста в реализации
- понятна игрокам
- легко тестируется
- хорошо подходит для первого рабочего релиза

Для `2v2` рейтинг можно считать через ожидаемый результат команды по среднему или агрегированному рейтингу ее участников, а затем записывать индивидуальное изменение каждому игроку.

### 3.7 Правила подбора персонажей

Подбор персонажей должен быть не захардкожен в формулу, а вынесен в конфигурацию.

Нужен отдельный модуль правил, который:

- вычисляет разницу рейтингов между игроками или командами
- определяет допустимый диапазон силы персонажей
- автоматически возвращает пул доступных персонажей
- позволяет позже подключить дополнительные ограничения

Это даст возможность потом добавить:

- баны персонажей
- особые ограничения турниров
- отдельные настройки для разных режимов

## 5. Ключевые пользовательские сценарии

### 5.1 Сценарий матча `1v1`

1. Админ создает матч.
2. Выбираются два игрока.
3. Система автоматически рассчитывает допустимых персонажей.
4. Игрокам назначаются персонажи из доступного пула.
5. После офлайн-матча админ фиксирует победителя.
6. Система пересчитывает рейтинг и сохраняет историю изменений.

### 5.2 Сценарий матча `2v2`

1. Админ создает матч.
2. Формируются две команды по два игрока.
3. Система рассчитывает баланс по командам.
4. Для каждой стороны определяется допустимый пул персонажей.
5. После матча фиксируется победившая команда.
6. Система обновляет рейтинг всем четырем игрокам.

### 5.3 Сценарий турнира

1. Админ создает турнир нужного режима.
2. Добавляет участников.
3. Система строит сетку по рейтингу.
4. Каждый матч сетки создается как обычный матч.
5. Результаты матчей продвигают участников дальше по сетке.
6. Все результаты попадают в историю и влияют на общий рейтинг.

## 6. Архитектурный подход

Если проект начинается с нуля, прагматичная стартовая архитектура такая:

- `Next.js` для интерфейса и серверных обработчиков
- `TypeScript`
- `PostgreSQL`
- `Prisma` или `Drizzle`
- серверная аутентификация через `NextAuth` или аналогичный проверенный механизм

Почему это подходит:

- одна кодовая база для UI и backend-логики
- удобно строить админку
- проще разрабатывать CRUD, авторизацию и серверные сценарии
- меньше инфраструктурной сложности на старте

## 9. Логика автоматического подбора персонажей

На первом этапе лучше использовать конфигурируемую таблицу правил.

Пример идеи:

- если разница рейтинга маленькая, оба игрока получают доступ к широкому пулу персонажей
- если разница средняя, более сильный игрок получает менее сильных персонажей
- если разница большая, сильному игроку доступны только слабые тиры, а слабому более сильные

Важно:

- не кодировать логику только через тиры
- хранить и тир, и числовую силу
- выбирать персонажей автоматически на основании конфигурации
- логировать, по какому правилу был сделан подбор

Это нужно для дальнейшей калибровки баланса после реальных игр.

## 10. Тестирование

Минимально необходимы:

- unit-тесты для расчета рейтинга
- unit-тесты для автоматического подбора персонажей
- unit-тесты для определения победителя и завершения матча
- unit-тесты для построения турнирной сетки
- интеграционный тест на сценарий `создание матча -> подбор -> результат -> рейтинг`
- интеграционный тест на турнирный сценарий

Отдельно важно проверить:

- права доступа
- невозможность выполнять админские действия без роли
- корректность обработки отмененных матчей
- консистентность данных при повторной отправке результата

## 11. Риски проекта

Главные риски:

- неудачная первая версия формулы баланса персонажей
- смешение понятий `игровой рейтинг игрока` и `сила персонажа`
- усложнение модели `2v2`, если сразу не ввести сущность команды или стороны
- дублирование логики матчей и турнирных матчей
- слабая модель прав доступа

Как снижать риски:

- делать конфигурируемые правила вместо жестко вшитых
- строить турниры поверх обычных матчей
- сначала довести до конца вертикальный срез `1v1`
- покрыть ядро доменной логики тестами до UI-полировки

## 12. Что изменилось после уточнений

По сравнению с первоначальным черновиком плана зафиксированы следующие решения:

- рейтинг теперь общий, а не сезонный
- подбор персонажей должен быть полностью автоматическим
- режимы первой версии ограничены `1v1` и `2v2`
- авторизация стала обязательной частью `MVP`
- баны персонажей не входят в первую версию, но архитектура должна поддержать их позже
- повторное использование персонажей в турнире разрешено без ограничений
