# Руководство администратора и локальный запуск Unmatched Tier

## Назначение системы

`Unmatched Tier` нужна для ведения игроков, каталога персонажей и рейтинговых матчей по `Unmatched`.
Администратор управляет игроками, героями, матчами и контролирует корректность рейтинга.

## Локальный запуск

### Что нужно заранее

- `Node.js` 22+ или совместимая актуальная LTS-версия
- `npm`
- доступ на запись в каталог проекта

### Установка зависимостей

```bash
npm install
```

### Переменные окружения

Создай `.env` в корне проекта. Минимально нужны:

```env
DATABASE_URL="file:./dev.db"
SESSION_SECRET="change-this-secret"
SEED_ADMIN_EMAIL="admin@example.com"
SEED_ADMIN_PASSWORD="admin12345"
```

Рекомендации:

- `SESSION_SECRET` должен быть длинной случайной строкой
- `SEED_ADMIN_EMAIL` и `SEED_ADMIN_PASSWORD` используются при локальном seed

### Подготовка базы данных

```bash
npm run db:push
npm run db:seed
```

После этого локальная SQLite-база будет создана, а в системе появятся:

- стартовые `RuleConfig`
- стартовый каталог героев
- администратор из `SEED_ADMIN_EMAIL`

### Запуск проекта

```bash
npm run dev
```

Приложение будет доступно по адресу `http://localhost:3000`.

### Production-проверка локально

```bash
npm run build
```

Если сборка проходит, значит типы, Prisma-схема и маршруты находятся в согласованном состоянии.

## Первый вход

1. Открой `/login`.
2. Войди под пользователем из `SEED_ADMIN_EMAIL`.
3. После входа станут доступны административные действия.

## Основные разделы

### Players

Администратор может:

- создавать игроков
- открывать карточку игрока
- вручную менять текущий рейтинг

Важно:

- ручная правка меняет только текущее значение рейтинга
- уже сыгранные матчи автоматически не пересчитываются

### Heroes

Администратор может:

- добавлять героя вручную
- выбирать `tier` из списка `S`, `A`, `B`, `C`, `D`
- выбирать тип боя: `ближний` или `дальний`
- указывать `power score`
- загружать изображение
- удалять одного героя
- удалять весь каталог героев сразу

Важно:

- героя нельзя удалить, если он уже участвовал в матчах
- массовое удаление каталога тоже блокируется, если герои уже использовались

### New Match

На странице создания матча администратор:

- выбирает двух активных игроков
- создаёт матч `1v1` в статусе `DRAFT`

### Match Details

Основной сценарий администратора:

1. Назначить героев автоматически.
2. Перевести матч в статус `READY`.
3. Выбрать победившую сторону.
4. Зафиксировать результат.

После фиксации:

- рейтинг игроков пересчитывается
- матч попадает в историю

### Leaderboard

Показывает актуальный рейтинг игроков.

### History

Показывает журнал сыгранных матчей и результатов.

## Как добавить героя

Заполни поля:

- `Name`
- `Slug`
- `Tier`
- `Тип боя`
- `Power score`

Рекомендации:

- используй короткий и стабильный `slug`
- выбирай `tier` только из утверждённого списка
- `power score` должен соответствовать вашей локальной модели баланса

## Когда менять рейтинг вручную

Используй ручную корректировку только в исключительных случаях:

- исправление стартового рейтинга
- калибровка после тестовых игр
- исправление ошибочного ввода

Не стоит использовать это как замену обычной фиксации матчей.

## Типичный рабочий сценарий

1. Проверить или добавить игроков.
2. Проверить каталог героев.
3. Создать матч `1v1`.
4. Назначить героев.
5. Перевести матч в `READY`.
6. Зафиксировать результат.
7. Проверить изменения в `Leaderboard` и `History`.

## Частые проблемы

### Seed не создаёт администратора

Проверь:

- задан ли `SEED_ADMIN_EMAIL`
- задан ли `SEED_ADMIN_PASSWORD`
- успешно ли выполнился `npm run db:seed`

### Не видно новых полей или Prisma ругается на схему

Выполни:

```bash
npm run db:push
npm run db:seed
```

Если проблема остаётся, проверь, что `DATABASE_URL` указывает на ту же локальную базу, с которой работает приложение.

### Не запускается dev-сервер

Проверь:

- что зависимости установлены
- что порт `3000` не занят
- что `.env` заполнен

## Осторожно

- не удаляй весь каталог героев без необходимости
- не меняй рейтинги массово без отдельного решения
- перед крупными изменениями в базе полезно сделать backup `dev.db`
